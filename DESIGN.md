# DESIGN.md · cake's design standard: shadcn/ui components + the Frosting theme

This is the **single design standard** for every cake interface: the home page after install, the dashboard, Session replay (the session list and each session's replay), settings, and any page added later.
Read this file before you change any interface, follow it, and when you are done pass the three checks in §12.

The pages come in two styles (§17): **Minimal**, a plain look and the default, and **Cake**, the look this file describes. Minimal changes only the colours, the fonts and the frame, through its own tokens and the components' `minimal:` classes; every rule in this file holds in both.

In one sentence: **every component is shadcn/ui (React + Radix), and every look comes from one set of theme tokens, "Frosting"**. The cartoon feel comes from the mascot Crumb, the illustrations and the theme's uniform thick outline + hard shadow; the component structure stays exactly as shadcn ships it.

- Code: `web/` (Vite + React + TypeScript + Tailwind + shadcn CLI). For a release, `npm run build` compiles it into static files in `web/dist/` that go into cake's package; the Python process only serves static files and JSON. Users never install Node.
- The only implementation of the tokens: `web/src/styles/tokens.css` (variable names follow shadcn). Tailwind only maps them to class names (`@theme` in `web/src/index.css`, which holds no values).
- Components: `web/src/components/ui/` (generated by the shadcn CLI; the Frosting changes are written in the components); cake's own components: `web/src/components/cake/` (built only from ui components and tokens); pages: `web/src/pages/`.
- Component overview: `#/components` (like the shadcn docs: every component and every variant on display). Each block names its components in code type, says in plain words what the reader sees and when (one or more paragraphs), and lists the code it relies on (props, tokens, files, the API it reads) on one line in the same code type.
- Data: pages hold no data. They read cake's JSON API (`/api`) through `web/src/data/` (types, JSON Schemas, and sample answers that only the screenshot and dev servers use); `web/README.md` lists the endpoints.
- Checks: `npm run check:ui` (rules + this file's token table + the `/api` contract), `npm run visual` (screenshots compared pixel by pixel with the baseline).

## 1. Principles

1. **Human or agent at a glance.** The session categories (the three verdicts Human, Agent and Script bot, a Human session cake couldn't tell marked limited evidence, an Agent session split into Agent only and Human + agent, and which agent by name) have one set of colors, one set of icons and one set of words across the whole site (§3.1).
2. **The reasons are always visible.** Next to every verdict you can see, or click through to, the four layers of reasons (name, verification, environment, behavior); layers that are off are shown too.
3. **One kind of thing has one look.** A button is shadcn's `Button`, a card is `Card`. A new look can only be a new variant on a component, written into §6 of this file; **pages may not restyle anything on their own** (the check script blocks it).
4. **Cartoon, not childish.** The cartoon comes from Crumb, the illustrations, and the uniform outline and hard shadow; numbers, charts and reasons use normal typography.
5. **Everything local, in plain words.** Fonts, icons and illustrations are all bundled; copy is short, buttons are verbs, nothing is overstated (§2).

### 1.1 Scope: record everything, highlight Agent sessions

AgentCake records every session and keeps them all, but the sessions where an agent acted are the ones it highlights.

- **Record everything, keep everything**: Human, Agent and Script bot sessions are all recorded and all kept; by default nothing is deleted by age (0.3.4 `retention_days 0`).
- **Highlight Agent sessions**: an agent from start to finish (Agent only) or a human and an agent taking turns (Human + agent). On every page they come first and stand out most (§6.1). (The industry's words, Human / Agent / Unknown / Bot, with Agent split into Agent only and Human + agent, replaced "Human + agent" for the whole group and "Mixed".)
- **Human is the comparison group**: shown normally, not muted. **Script bots are not highlighted**: only counted and filterable, muted in lists, kept out of agent charts.
- **Disk**: the budget defaults to 10 GB; at 80% the settings page and the dashboard warn (the dashboard shows no other disk information; the numbers are in Settings). "Automatic cleanup" is on by default: when less than 10% of the budget is left, it deletes the oldest session replays across all session types until use is under 90% (a replay still being recorded waits until its session is quiet; visits and verdicts stay). When it is off and the budget is full, new replays stop being stored, visits and verdicts are still collected, and the session records how many events were dropped. While the disk itself is below its floor (`disk_min_free_mb`), new replays stop and none is deleted. Choosing 90- or 30-day retention also deletes sessions with an agent by age, and the settings page must say so. (As in cake 0.3.4, fce7503)

## 2. Voice and tone

- Short sentences, active voice, second person. Buttons name the action ("Watch replays", "Copy", "Delete all data"), never "Submit" or "OK".
- Classifications are Human / Agent / Script bot (an Agent session is Agent only or Human + agent; a Human session cake couldn't tell is marked limited evidence), never "Suspicious" or "Fraud". The model's confidence is shown on the session page, as the calibrated percent next to the classification and each layer (§6.4), never as an accuracy figure.
- Empty states say what to do next; errors say what happened and what to do. At most one playful line per screen, and no jokes in numbers or reasons.
- Interface text is in English for now, the sentence for the coding agent too (the Chinese README quotes it in Chinese).
- **Counts** have a comma between thousands, as PostHog and the rest of the industry write them ("1,900"): `integer()` in `src/lib/format.ts` writes every count the pages show (the cards, the Agent block, the charts' values, hovers and axis, the tables and their hovers, the session list's chips, a session's pages and actions), and a sentence with a count in `WORDS` takes it written so. The API's numbers stay plain.
- **Who acted: only these words**: words about classifications are only Human / Agent / Script bot, Agent only / Human + agent, limited evidence, and Unknown only for a stretch or a layer that couldn't tell (plural Humans / Agents); person / people / user are never used for visitors: "Human" and "Agent" tell them apart more precisely. Examples: "Human + agent sessions", "A human", "Human sessions", "Sessions where an AI agent acted on behalf of a human", "Human only". A count is named by what it counts, in sessions: "Sessions" (a total is named by its metric alone, as "Visitors" and "Page views"), "Agent sessions" ("1 session" in the singular). These sentences live in `WORDS` in `web/src/lib/words.ts`; text that comes with the data (session titles, reasons, the Script bot help) comes from cake's API and follows the same rule. `npm run check:ui` blocks person / people and "PostHog" in interface text (comments excepted), and also "user" for a visitor in the API samples ("user agent" is fine). Headings and buttons use sentence case.
- **Product name**: publicly it is "AgentCake" (decided 2026-11-12, spelled as one word since that evening; the command and package name is agentcake). The name in the interface comes only from `name` in `agentcake/data/product.json`, which the pages read when they are built (`vite.config.ts` gives it to them as `VITE_PRODUCT_NAME`): the browser title (`%VITE_PRODUCT_NAME%` in `index.html`) and the components (`PRODUCT_NAME` in `src/lib/product.ts`: the top bar, the home page, Crumb's screen-reader name, the error that says cake can't be reached, and the sentences that mention the product in settings and the component overview); components never hard-code it. Text that comes from cake's API (reasons, the coverage table) arrives with the name already in it. Wherever a sentence refers to the product, either use `PRODUCT_NAME` or rephrase it so no name is needed ("Why this classification", "How detection works", "Classification"). The mascot Crumb and the cake theme stay. Commands in code blocks use the command's name, `agentcake …` (`command` in `agentcake/data/product.json`).

### 3.1 The session categories (the same everywhere)

Settled on the words the industry uses, with no kinds of agent (agents are listed by name): one word each, written once in `agentcake/data/judging.en.json`, which the pages read when they are built (`web/src/lib/taxonomy.ts`) and the API's words use too, so every badge, filter, block and sentence says the same word.

1. **Verdict**, one per session, together every session: Human, Agent, Script bot. An Agent session is **Agent only** (an agent from start to finish) or **Human + agent** (a human and an agent took turns; the timeline marks each hand-off). A session cake can't tell (too few actions, a phone or tablet it can't confirm, evidence too weak or pointing both ways) is Human, marked **limited evidence**: its reasons say which. A phone or tablet whose screen and touch support fit the device, with nothing found by the other layers, is a Human like any other; a phone or tablet shown as Human shows no percent. There is no Unknown category: what cake can't tell goes into Human, marked. A stretch of a session the behavior model couldn't tell is no verdict: it reads Unknown in bars, timelines and the reasons panel's layers. A prefetch that was never shown is no visit and in no category.
2. **Which agent**: the product's or the automation tool's name (Claude in Chrome, ChatGPT, Playwright, Selenium…) and how sure it is, Verified (a signature or a published address range) or Likely (the name it gives, or the product's or tool's own traces); **Unnamed** when no name fits (what was seen, such as automation markers that don't show which tool, is in its reasons). What kind of agent it is (an AI in a real browser, an automated browser) is a reason too, never a category: a human may be running Playwright or Selenium as much as an AI is.

Every category badge has one shape: a pill with the `--line` frame, a dot with its icon, the word, and its own colours: all the labels have the same height and look.

A stretch of a session the behavior model couldn't tell (the actor `unsure`) and a layer that couldn't tell read Unknown, with Unknown's look; a session never does.

- The blue / orange pair was tested with the dataviz skill's `validate_palette.js`: everything passes (color-blind ΔE 24.7, normal vision 33.6, ≥ 3:1 against the background). Gray is deliberately not a categorical color; it is told apart by texture and dashed lines.
- Text contrast (dataviz `contrast()`): at least 4.55:1 (`--faint-foreground` on `--muted`), badge text 5.26–5.50:1.
- `--primary` (strawberry pink) is only for the primary button and the mascot, **never for data**. ok / warn / destructive only show system status, never verdicts.

## 4. Fonts

Headings **Fredoka** (`font-heading`, used automatically for h1–h3), body text **Nunito** (`font-sans`), code in monospace. Minimal (§17) sets body text and headings in **Inter**; the logo's wordmark and Crumb's "z" stay Fredoka in both styles (`font-logo`). All are SIL OFL 1.1; the files are in `web/src/assets/fonts/` (with OFL.txt), bundled by Vite, never loaded from the internet.

## 5. Shape: the cartoon frame is part of the theme

- Every "framed" component uses the same frame: `border-2 border-line` + `shadow-hard` (large blocks) or `shadow-hard-sm` (buttons, rows), already written into the components themselves (the "Frosting changes" column of the §6 table). **Pages add no further outlines or shadows.**
- Hover: moves 1px up and to the left and the shadow grows; press: moves down and to the right and the shadow disappears (Button, SessionRow).
- Radius: `--radius` 0.875rem; cards `rounded-2xl`, buttons `rounded-lg`, badges / selects / switches `rounded-full`; a checkbox keeps a small square radius (5px), so it never reads as a round pick-one control.

### 6.4 The replay page

- **One clock, one count**: every moment on the page (the player, the timeline and its hand-off marks, the reasons, the summary, Pages visited, All actions, Server middleware) counts from the recording's start and is written as the player writes it (`0:47`); the line under the title gives when the session started, how long its recording runs (the player's length, as the session list gives it) and how many pages it went to (the rows of Pages visited).
- **The header** names the session as §3.1 sorts it: `VerdictBadge` (with `ThinEvidenceTag` for a Human session on limited evidence), then for an Agent session `TurnsBadge`, then the agent's `AgentTag` with how sure its name is inside it, lower case ("Claude in Chrome · likely"), or `UnnamedTag`. The verdict badge carries how sure cake is (`percent` in `/api/session`), bold on the highlighter: "Agent · 94%" (the combined percent marked and bold, and each of the four steps with its own); a Human classification on limited evidence shows its own chance, which is lower ("Human · 55%"), beside the mark. In "Why this classification", each layer's badge shows the side its evidence leans to with its percent ("Agent · 99%"; a behavior layer that found a human and an agent taking turns stays "Human + agent · 97%"); a layer that judged nothing (No findings, Not used, too little data) has no percent. No percent shows when the API gives none, as for a phone or tablet shown as Human, on limited evidence or not (the behavior model isn't used there). The percent is the page's only word on how sure the verdict is: the summary above the layers says who acted when and which layers support the verdict (those whose conclusion is the verdict's), each with the percent its badge shows. A layer's badge is its conclusion; its percent is how sure the layer is of that conclusion and shows only when it agrees with it; a layer less than half sure of its conclusion says Unknown, without a percent, and its first line says its evidence points both ways. A layer lists only its own findings (a name read off a trace in the page shows under Environment, where the trace is), only the ones that fit its conclusion, and a sentence read from two places once (its detail names both). The behavior layer follows the timeline: Human + agent, "A human and an agent took turns in this session.", when the timeline has hand-offs, the verdict's own side when it has none. A Script bot whose environment layer found automation says why it is still a Script bot.
- **The player** is rrweb-player 2.0.0-alpha.18 (MIT), the copy cake ships in `agentcake/static/`: the pages load `static/rrweb-player.umd.cjs` and `.css` when a replay opens (no npm copy; the dev, screenshot and test servers serve the same two files). Its frame sits on the stage's `--muted`; nothing of its own controller is shown.
- **Chunks**: the player reads the chunks its first moment needs plus the next one, reads each next chunk as playback enters the one before it, and reads every chunk before a moment it jumps to (rrweb rebuilds a page from its last full snapshot), never the whole replay at once. If playback ever gets ahead of the chunks it waits ("Loading the next part…") and goes on.
- **The cursor carries the name of who acts** at that moment: the agent's name ("Agent" when it has none), "A human" or "Unknown", in a pill under the pointer in that side's soft colour and text colour (`--agent-soft` / `--agent-foreground`, `--human-soft` / `--human-foreground`, dashed `--unsure-soft`), framed in `--line`; the click ring and the pointer's trail use `--agent` / `--human` / `--unsure`. The pill keeps the interface's size whatever the player's scale. The rules are in `index.css` ("Replay player"), built from the theme with `@apply`; no colour is written there.
- **Who acted, when** under the player: `SessionTimeline` with the playhead; it moves the replay. Under it, each actor's share of the session's actions ("Share of actions: Human 77%, Agent 23%, Unknown 0%"), its `MiniTimeline` in the order they first act on the timeline; "No actions recorded" when there are none. An action is what All actions lists (a click, typing, a scroll) everywhere on the page: the share and the Actions column of Pages visited count the same ones. Two hand-off labels too close to sit side by side take two rows, so each stays readable at 485 px. "Jump to hand-off" (`Button ghost`, only when the session has a hand-off) starts the player `handoff_lead_ms` before the next hand-off (a cake setting that comes with the session, 3 s by default), going round to the first after the last.
- **Pages visited** under it (`SessionPages`, `pages` of `/api/session/<id>`: which pages the session went to, the page it came in on and the page it left from): first the entry page and the exit page, then a `Table` with a row per page in the order it opened: when (`Button link` `xs`, like All actions), the path, the time on page, who acted there (`WhoBadge`: Human, Agent, Human + agent, or Unknown when all its actions are stretches cake couldn't tell; a dash for a page without actions) and its actions (`max-md:hidden`). A replay cut short while the disk was full plays what is left, with an `Alert warn` under it. A replay with no page recorded up to the playhead (no page snapshot before it, as in a recording made without page content) plays the pointer and the clicks on the empty stage, with an `Alert info` under it saying so; the note goes once a page is there. A replay that can't load shows Crumb `oops`, what happened and "Try again".
- **Sessions of more than one tab**: a session is a visit, every tab of one browser while no 30 minutes pass without activity in any of them, 24 hours at most, as PostHog's are; each tab is still classified on its own, and the session's classification is made from its tabs'. The address bar names the tab on the stage (`Badge tag` "Tab 2"). A session of one tab shows none of this: its page is the page it always was.
- **Server middleware**: a `Table` in a `Card`, one row per page request (time, page, Sec-Fetch site · mode · dest · user, signature, cake.js network match; the Sec-Fetch and signature columns are `max-md:hidden`), the network line above it in server mode (with `SourceCredit` at its end when the country comes from the city database), and cake's sentence when there are no rows.
- In **All actions**, each time is a `Button link` `xs` that moves the replay there.

- **Delete session** beside the header opens `DeleteSession`. The dialog shows the session's title, start time and ID. It confirms that deletion removes the whole visit, including the replay and every tab, even if a tab's address opened the replay. Confirming waits for the local API to finish. An error or cleanup warning stays in the dialog. Success opens the session list and reloads its totals. The back link and deletion both restore the filters carried from the list.

Then, as `SettingRow`s in `Card`s: where visits come from (your website on this computer or on a server, the server middleware), each with `Status` and when it last sent something, asked again every `refresh_ms` while the page is open, without touching what is being edited; an `Alert warn` naming the headers the site's server never got; keep data (retention, `StorageUse`, `BudgetWarning`, budget, "Automatic cleanup"); the page script's two settings: "Extra automation detection" (`hook_dom` as a `Switch`, off by default) and "Mask elements" (the hide selectors as an `Input` that is saved only when the browser reads it as CSS selectors); how it decides (the four layers and the lists' date, shown with `Badge tag`, never as switches that can't switch: each layer says where it works, "Local or server", or "Server only" for Verification), and under them "Automatic updates" (`lists_auto_update` as a `Switch`, on by default: the lists, and on a server the city database, downloaded once a month), whose description says when the last update ran and how it went; failed updates in a row bring an `Alert warn` with the command in a `CopyBlock`, as lists past their age limit do; telemetry and registration (what was sent, how to have it deleted); and "Delete all data" (`Button destructive` + `Dialog`). No control without a feature behind it. The cards come in rows of two (`Columns 1-1 equalHeight`): your website and the page script; where visits come from and how it decides; keep data beside registration and your data (stacked, the last one filling the row), so each row's cards start and end together.

## 13. Don'ts

- Don't style buttons, cards or inputs yourself in a page; don't hard-code colors or sizes; don't use Tailwind palette colors; don't add outlines or shadows in a page.

- Don't load fonts, icons, scripts or images from the internet; don't use other companies' illustrations or trademarks; from 21st.dev and the like borrow only the look, and before using their code check the license and write it into §14.
- Don't write "Coming soon"; don't delete sessions by age by default; don't automatically delete sessions with an agent; don't hide human-only sessions; don't highlight script bots.
- Don't show visitors' IPs, emails or account ids in the interface; sessions use a short hash.

## 15. Agent avatars (blobs)

Decided on 2026-11-12: the avatars sway gently while idle and look cute; of the three looks tried (Flat, Depth, Cartoon), they are made in Flat. The reference was a screenshot of the x.ai/bot page (a row of flat-colored blobs with white pill eyes): we borrowed only the feel of "flat blobs + swaying while idle" and did not scrape that page; the shapes and the eyes are our own.

- **Shapes**: 8 dessert blobs: `mochi`, `gumdrop`, `macaron`, `donut`, `pudding`, `scoop` (a scoop of ice cream), `cookie` (a cookie with a bite taken out), `dumpling` (a steamed bun). Self-drawn SVG (`web/src/components/cake/avatar.tsx`). The eyes are Crumb's kind: white eyes + ink pupils (not white pill eyes), and a small curved mouth; the outline uses `--cake-outline`, like Crumb.
- **Colors**: 6 avatar color tokens `--avatar-1..6` (the §3 table), flat fills, **for avatars only, never a verdict**, not used in charts, badges or timelines. **Unnamed is the only grey avatar, because it has no name** (the owner decided on 2026-11-15): always the `scoop` (not the plain `mochi`, which Claude in Chrome's avatar is), filled with `--unsure`, the grey Script bot and Unknown use, so the interface keeps one grey; its beat still comes from its name. They stay apart from the verdict colors: with the dataviz method (OKLab ΔE×100, Machado 2009 color-blindness simulation), each avatar color is measured against the solid and the light colors for human / agent / unknown; it needs ≥ 15 for normal vision and ≥ 8 under red-green color blindness; `npm run check:ui` recomputes this on every run (now: ΔE ≥ 15.0, color-blind ≥ 8.0). Avatars are not guaranteed to stay apart from each other under color blindness; shape and name tell them apart.
- **One fixed avatar per agent**: name → hash → shape + color + rhythm (`avatarOf()`; Unnamed's shape and color are fixed, above). No hand-kept list: a new agent gets one automatically, and the same name has the same avatar on every page. Different agents may land on the same shape, but the name is always beside it.
- **Decoration only**: the SVG is `aria-hidden` and the name is always written beside it; no vendor logos, brand colors or mascots. Humans and script bots have no avatar (script bots are not highlighted).
- **Motion**: a gentle sway while idle: rocking ±4° side to side, bobbing up and down, a little squash and stretch, one cycle every 2.1–3.2 seconds; each avatar's rhythm and starting point are offset (`data-phase` 0–5), so a row of avatars never moves in step; a blink every 4.4–6.6 seconds. Crumb's idle poses sway and blink the same way (§7). Under `prefers-reduced-motion` nothing moves (the global rule in `index.css`).
- **Used in**: session rows and compact rows (before the name, after the Agent session's Crumb marker, inside `AgentTag` or `UnnamedTag`), the spotlight block's agents by name (Unnamed too), the y-axis of the dashboard's "Top agents" (`AgentTick`: avatar + name, Unnamed too; a long name wraps to two lines, the whole name on hover), the agent tag on the replay page title (`AgentTag`, or `UnnamedTag`), and the avatars' block of the component overview. Not used for chart data colors, the reasons panel or table numbers.
- **Size**: 20px in rows (as tall as the name, so rows don't get taller), 16px in tags, 20px on chart y-axes, 56px in the component overview.
